# 产品需求文档

## 1. 引言
### 1.1 编写目的
本文档作为《软件工程导论》课程实践任务的**初版需求文档**，旨在明确“学院学生综合服务与党团管理平台”的功能与非功能需求。本文档综合了初始需求及甲方需求讨论会议的结论，为后续的系统设计（如用例分析、数据库设计）、编码实现及系统测试提供基准依据。

### 1.2 项目背景
目前学院学生事务（如党团流程、证明开具、政策咨询、就业通知等）主要依赖人工处理和微信群转发，存在重复性劳动多、信息滞后、学生对流程不熟悉等痛点。为此，需开发一套高度集成化、智能化的管理系统。

### 1.3 核心目标与范围
打造一个“一站式”服务窗口，实现事务办理电子化、政策咨询智能化、信息推送精准化，从而提升学生办事效率，减轻学院教务与学工老师的管理负担。

## 2. 综合描述
### 2.1 产品形态与技术选型
- **操作端点**：采用**前后端分离的网页版方案**（响应式设计）。手机端侧重于处理简单、高频任务（如查看通知、申请请假）；电脑端侧重于处理复杂任务（如后台管理、数据批量导入导出、审批）。
- **数据库**：人大金仓（Kingbase）数据库。
- **数据交互**：由于无法直接对接校级“微人大”系统接口，系统必须支持通过 Excel/Word/PDF 等格式文件的导出与批量导入来进行数据初始化与日常同步。

### 2.2 用户特征与角色权限
目标用户群体主要为学院约 **1000-1200 名**在校本科生及研究生，以及相关的管理教师。系统权限严格划分为以下4个等级：
1. **一级（学院领导）**：拥有最高数据查看权限，关注平台宏观运行与数据统计。
2. **二级（管理老师/辅导员/班主任）**：核心管理者，负责数据上传、动态维护及各类业务的审批。
3. **三级（班团骨干/团支书/班长）**：拥有部分管理权限，协助录入信息，对接学生与学院事务。
4. **四级（普通学生）**：终端用户。仅能查看、操作个人相关数据，无任何数据导出或他人数据审批权限。

*(注：助教原则上不开放审批权限。系统需强制记录所有管理员的**操作日志**以备溯源。)*

### 2.3 假设与依赖关系
- **环境依赖**：需学校或公司提供部署服务器及人大金仓数据库环境。
- **通知渠道依赖**：优先依赖邮件及微信服务通知通道，短信通知因涉及第三方费用，本期仅作模拟记录。

## 3. 系统功能需求详述
根据甲方会议结论，功能模块按优先级（P0-P2）进行划分：

### 3.0 全局功能：身份验证与登录（基础支持）
- **实名认证**：基于微信账号实名制体系，对接学生基本信息（学号、姓名等）进行身份绑定与验证。

### 3.1 智能问答与知识政策库（优先级：P0）
- **政策文档管理**：支持管理老师手动上传、更新政策文件（如奖助学金、休学复学、宿舍调整等），单文件最大支持 30MB。
- **智能咨询匹配**：支持关键词搜索或AI匹配，为学生提供即时咨询回复。
- **回复约束**：必须优先基于标准答案或官方文件链接回复，严禁大模型生成“幻觉”；敏感信息不直接展示，仅提供官方链接。
- **模板下载**：提供常用证明、请假条、活动预算表、简报等标准 Word/Excel 模板的下载服务。

### 3.2 党团事务流程管理（优先级：P0）
- **流程可视化**：系统内置固定的标准时间线，展示入党/入团全流程（入党申请人 → 积极分子 → 发展对象 → 预备党员 → 正式党员）。
- **进度追踪与提醒**：学生可随时查询当前所处阶段。系统根据时间节点自动触发关键任务提醒（如：积极分子满 3 个月需提交思想汇报）。

### 3.3 奖励荣誉展示（优先级：P1）
- **荣誉公示墙**：展示国奖、校优等重要荣誉获得者的信息，发挥榜样表率作用。

### 3.4 学生画像与信息管理（优先级：P1）
- **多维度画像**：整合学号、专业、年级、科研竞赛、社会实践等维度数据，形成完整的学生电子档案。
- **数据维护**：支持管理员批量导入信息，支持学生个人补充完善信息（需经老师审核生效）。

### 3.5 信息集成、证明生成与审批流（优先级：P1）
- **信息聚类与精准推送**：自动抓取或人工录入校内公众号通知。对信息打标签（如“就业”、“实习”），结合学生画像（年级、专业）进行精准推送。
- **多渠道通知分发**：支持通过平台内消息、邮件或微信提醒转发信息。
- **证明自动生成**：系统自动调用数据库中的学生基础信息（姓名、身份证号、入党时间等），填充至标准证明模板，自动生成 PDF 预览文件。
- **电子审批流**：支持请假、盖章等业务的在线电子审批。提供**异常处理机制**：允许老师在规定期限内（如 1-2 天）撤回或重批审批结果。

### 3.6 学业情况分析与预警（优先级：P2）
- *(注：因数据高度依赖学生主动上报且教务对接困难，此模块作为低优先级延展功能。)*
- **培养方案比对**：录入各年级/专业培养方案。
- **成绩分析与建议**：学生上传成绩单（支持 PDF 解析），系统对比培养方案高亮未修满学分模块，并推荐本学期开设的相关专业课程（仅做类型匹配）。

## 4. 外部接口与非功能需求
### 4.1 外部接口与界面需求 (UI/UX)
- **界面体验**：界面需符合现代Web审美，兼顾PC端与移动端浏览体验。UI展示与交互创新占课程评分的 20%，需重点优化智能问答与流程可视化界面的易用性。
- **文件接口**：支持标准 Excel/Word/PDF 文件的双向解析与生成。

### 4.2 安全性与数据隐私
- **敏感信息保护**：身份证号、生源地、户籍地、导师信息、修学/延毕记录等需严格加密存储，**仅管理员可见**。
- **公开信息边界**：学号、民族、班级、专业等基础数据可适度公开。

### 4.3 性能与并发需求
- **并发处理**：系统需稳定支持学院约 **1200 人**的并发使用规模，确保选课季或通知下发时的访问流畅。

### 4.4 可靠性与可维护性
- **数据一致性**：依托 Kingbase 数据库的事务机制保证数据不丢失、不篡改。
- **架构扩展性**：采用模块化开发，代码结构必须稳健，坚决避免“补丁式”开发，确保后续课程迭代时可方便地增加新功能（如出国申请、评价评优等）。

## 5. 课程交付物与验收标准
### 5.1 交付物列表
1. **软件产品**：前后端分离的系统源码及部署上线的可运行版本。
2. **技术文档**：包含需求文档（本文档）、数据库设计说明书、API 接口文档等。
3. **用户手册**：分别针对学生端和管理员端的操作使用说明。
4. **演示 PPT**：用于期末项目答辩及甲方（团委老师）验收评审。

### 5.2 评分与考核重点
- **实用性与业务完整度（80%）**：重点考察 P0/P1 核心业务流程（如党团流程、智能问答、电子审批）的逻辑闭环、防错设计与实际可用性。
- **创新性与 UI 展示（20%）**：重点考察大模型问答结合度、前后端分离架构的稳定性以及前端页面的响应式视觉效果。
